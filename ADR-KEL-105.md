# KEL-105 — platform second factor

Decision: use RFC 6238 TOTP (SHA-1, six digits, 30-second interval, ±1 step) rather than an external provider. A 32-byte key supplied as `PLATFORM_FACTOR_KEY` (64 hex characters) encrypts seeds with AES-256-GCM; store this key in the deployment secret manager, independently of `JWT_SECRET`, and retain it across replicas and restarts. Do not log it or back it up alongside encrypted database rows. Rotation needs a separately planned re-enrollment of every platform administrator; starting without a valid key fails.

An operator runs the existing `go run ./cmd/platform-admin -user-id <uuid>` after verifying the request out of band. Every invocation enables one enrollment, removes old TOTP material and challenges, and increments the factor version, thereby invalidating old platform JWTs and pending JWTs. Audit the command's actor/change ticket at the operations boundary; application logs record only the user ID, not seeds/codes/challenges. There is no password-only recovery endpoint. Existing assignments after migration remain unenrolled and need this operator step before login; old platform JWTs lacking a positive factor version are rejected.

Password verification returns a five-minute pending JWT, bound to the assignment's current version and usable only for challenge operations. Challenges are random 256-bit tokens (only their SHA-256 hashes persist), bound to user/purpose/version, expire in five minutes and allow five attempts. PostgreSQL assignment and challenge row locks serialize consumption; no Redis or client cookie is an authority. Successful enrollment increments the factor version; verified sessions have the version claim and remain tenantless. Identity checks live assignment and version on direct platform requests, and the gateway calls identity's session checker. Storage/verifier errors deny platform access. Browser stores pending/challenge JWTs in short-lived HttpOnly cookies; enrollment seed is displayed once to the user, never stored in browser persistence. Deployment order: migration and key before identity, then gateway, then web; old sessions are invalidated rather than grandfathered.
